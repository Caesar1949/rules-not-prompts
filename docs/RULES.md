# 规则编号体系

> 为什么规则要编号：Agent 引用规则时需要唯一标识。
> "别遍历导航路径" 这句话在对话里会被改写、被遗忘；`R001` 不会。

---

## 一、R 系列：禁止项

禁止项回答"不能做什么"，每条必须带**替代方案**。

只写禁止、不写替代，Agent 会换一种方式违反同一条规则。

| # | 禁止 | 替代方案 | 来源 | 作用域 |
|---|---|---|---|---|
| R001 | 遍历框架的私有导航结构 | 读路由单例的公开接口 | 架构约定 | 全局 |
| R002 | 展示层做业务计算 | 下沉到 ViewModel / Service | 架构约束 | 全局 |
| R003 | 混用包管理器 | 只用一种入口 | 工具链限制 | 全局 |
| R004 | 手改工程文件内部字段 | IDE 内配置 / 脚本 | 工具链限制 | 全局 |
| R005 | 引入未经批准的第三方 SDK | 优先系统框架 | 产品决策 | 全局 |
| R006 | 真实服务里嵌调试逻辑 | Mock 服务 + 工厂切换 | 项目约定 | 全局 |

### 来源的四种类型

| 来源 | 含义 | 谁能否决 |
|---|---|---|
| 架构约定 | 团队既有模式，改了会连带出问题 | 项目所有者 |
| 架构约束 | 产品形态决定，不是偏好 | 项目所有者 |
| 工具链限制 | 物理上做不到 | 没人能改，除非换工具 |
| 产品决策 | 人为拍板 | 项目所有者 |
| 项目约定 | 工程惯例，可随项目演进调整 | 项目所有者 |

**为什么标注来源**：Agent 面对"规则冲突"时，需要判断哪一条更硬。工具链限制不可能妥协；项目约定可以让步。

## 二、K 系列：执行方式

执行规则回答"怎么做"，与具体技术栈无关，可以跨项目复用。

| # | 规则 | 一句话 |
|---|---|---|
| K1 | 编码前先思考 | 先读后改 |
| K2 | 简洁性优先 | 复用现有模式 |
| K3 | 精准修改 | 只动目标代码 |
| K4 | 目标驱动 | 有明确成功标准 |
| K5 | 决策由人做 | 取舍交给人 |
| K6 | token 预算 | 超预算就暂停 |
| K7 | 冲突不平均 | 矛盾要上报 |
| K8 | 写前先读 | 禁止盲改 |
| K9 | 编译验证 | 没通过不算完成 |
| K10 | 通过即提交 | 不等全部做完 |
| K11 | 约定优于创新 | 新模式需确认 |
| K12 | 失败不沉默 | 立即报告 |
| K13 | 写 ≠ 完成 | 用 diff 验证落盘 |

### K 系列的排序逻辑

不是随意排列，按**时间顺序**走完一次修改：

```
K1 想 → K2 选方案 → K3 改 → K4 定标准 → K9 验证 → K10 提交
                                    ↑
                              K12 失败就报
```

K5 / K6 / K7 是**中断条件**：遇到就停，不要继续。

## 三、规则的生命周期

一条规则从哪来、什么时候该删：

| 阶段 | 触发条件 | 动作 |
|---|---|---|
| 产生 | 同一个错误出现 2 次以上 | 写进对应文件，附上事故描述 |
| 验证 | 下一次同类改动 | 确认规则真的被读到并生效 |
| 固化 | 连续 3 次没被违反 | 保持现状，不再强调 |
| 复审 | 技术栈 / 架构变化 | 重新确认是否仍成立 |
| 删除 | 前提条件消失 | 删掉，不要留"历史版本"注释 |

**不要保留已失效的规则**。规则文件里留着 `~~已停用~~` 的条目，Agent 会读到"存在过"这个事实，并可能按旧规则行事。

---

## 四、编号不要复用

删掉 R007 之后，不要给新规则继续编 R007。空号比错号安全。

如果规则含义变了（比如从"不要用 A"变成"不要用 A 的某个变体"），新建编号，并在 `CASEBOOK` 里记下变更原因。

---

## 五、状态层单独存放

规则层（`AGENTS.md`）回答"不能做什么"，状态层（如 `TRUTH.md`）回答"现在是什么"。

状态层只记录三类内容：

1. 能跑命令推导出来的 → **不记**（必然漂移）
2. 不会变的事实 → **不记**（属于架构文档）
3. **人的拍板 + 当前状态** → 记

判断标准：这条信息过一个月还成立吗？成立才值得写进状态层。

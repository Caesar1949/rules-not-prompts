# 案例集 — 规则拦住过什么

> 每条规则都应该能追溯到一次事故。
> 下面这些案例来自一个真实的单人 iOS 项目，已脱敏（去掉产品名、路径、账号信息）。
>
> 用法：当 Agent 违反某条规则时，把对应案例贴给它。案例比规则条文有效得多——
> 规则说"不要这么做"，案例说"这么做的代价是 7 轮调试和一次回滚"。

---

## 案例 1 · 编译通过，真机崩溃（R006 的反面）

**现象**：后台任务调度器注册后，每次系统唤醒都崩溃。编译期零警告，测试全绿，只有真机复现。

**根因**：类型标注了 `@MainActor`，注册 API 的回调参数是非隔离的。编译器在隔离闭包传给非隔离参数时，**插入了一个运行时隔离检查**——编译期完全看不到。而框架在后台线程回调，检查必然失败。

**代价**：定位靠反汇编比对符号表，读代码找不到。

**规则**：

- 会被系统在后台线程回调的注册型 API，承载它的类型必须 nonisolated
- 静态检查全绿 ≠ 运行正确；注册型 API 必须真机跑一次

## 案例 2 · 失败被伪装成成功（R006 的反面）

**现象**：用户点购买时失败，提示"网络异常，请检查网络"。本地开发环境完全正常。

**根因**：商店查询不存在的商品 ID 时**不抛错，返回空数组**。代码走进了 `try` 成功分支，日志打印"加载成功:"后面什么都没有。失败被伪装成成功，一路带到用户面前，还把排查方向甩给了网络。

**代价**：排查花了很久，因为错误文案在撒谎。

**规则**：

- 空集合 ≠ 成功，必须显式判空
- 错误文案按来源分级：商店没有商品、网络失败、系统异常是三件不同的事
- 日志里"成功"后面跟着空值，就是失败

## 案例 3 · 编译期的 warning 直接提交，绕过付费墙（R002 的反面）

**现象**：付费墙对免费用户完全无效，同时另一条路径上任何用户都报错。两处是同一个写法。

**根因**：`guard SomeEnum.case(...) == nil else { ... }`。这个表达式返回的是枚举值，不是可选值，`== nil` **永远为 false**，所以 `else` 分支必然进入。

编译器给了 warning："Comparing non-optional value to 'nil' always returns false"。**warning 被忽略了。**

**代价**：一处让免费用户绕过付费，一处让付费功能完全不可用。两个都是线上问题。

**规则**：

- 编译器 warning 必须当场处理，不能"先提交再说"
- 用公开的布尔属性做判断，枚举 case 只用于抛错信号

## 案例 4 · 测试汇总说全过，其实崩了（K9 的反面）

**现象**：构建输出里写着 `Executed 602 tests, with 0 failures`，同一份输出里还有 `TEST FAILED`。

**根因**：崩溃类失败不计入汇总行。汇总只统计断言失败。

**代价**：连续三次重跑，每次都以为是自己看错了。

**规则**：

- 看到汇总行全绿但整体失败，必须去 grep `Failing tests:` 段
- 测试隔离性缺陷（全局单例被并发用例改动）会让同一份代码有时过有时不过

## 案例 5 · 7 轮调试后回滚（K3 的反面）

**现象**：导航栏放 3 个右侧按钮时，标题始终不显示。依次尝试了 7 种方案：inline 模式、principal 插槽、large 模式、合并按钮到菜单、缩放字号、双保险、自定义 header。用户实测结果依次是：不显示、消失、错行、仍不显示、仍不显示、仍不显示、未实测。

**根因**：新版本导航栏对标题槽位的挤压规则没有公开文档，与按钮数量、文本长度、设备宽度多变量交互。**没有公开 API 能稳定实现这个组合。**

**代价**：7 轮 × 编译时间 + 7 次用户反馈，最后整体回滚。

**规则**：

- 涉及系统新版本 UI 行为的改动，先在真机/模拟器实测再提交，不要凭直觉改 modifier
- 连续两次方案失败后，优先 `git revert`，不要继续叠加方案
- 记录"当前能力上限"，比反复尝试更有价值

## 案例 6 · 一个 init 参数顺序，三处漏传（K3 的反面）

**现象**：用户保存的时间段显示成了保存时刻，不是选择器里选的时间。

**根因**：数据结构新增 4 个时间字段，加在 init 参数**末尾**。三个地方用"复制原对象 + 改几个字段"的方式构造新对象，只传了基础字段，末尾的时间字段全部落成 nil。

**代价**：用户报"时间不对"，两次加诊断日志才锁定是哪一个构造点。

**规则**：

- 结构体 init 没有"继承"语义，不显式传 = 默认值
- 字段增加后，所有 inline 构造点都要重新审视
- 提供统一的 `copyWith(...)` 辅助方法，而不是在各处手写拷贝

## 案例 7 · AI 写了 3,846 行没人调用的代码

**现象**：一次清理删掉了 3,846 行代码。删之前：编译通过、测试通过。

**根因**：这些代码从生产路径不可达。AI 在重构过程中生成了完整的视图、ViewModel、测试，但入口被删掉了，整条链路成了孤儿。没有任何报错，因为没人调用就不会报错。

**代价**：几千行代码在仓库里存在了很久，每次 Agent 读项目都要读它们，并可能基于它们做判断。

**规则**：

- 定期检查从入口不可达的代码（死链路清理）
- 删代码前先确认引用计数，而不是"看起来有用"
- AI 生成代码的真实成本不是"写得烂"，而是"看起来必要"

---

## 案例 8 · 规则文件里的失效条目误导了 Agent

**现象**：规则文件里写着"优先放进 Compatibility 目录做版本兼容"，但这个目录在重构中已经被删掉了。Agent 读到规则，开始往一个不存在的目录里写文件。

**根因**：规则更新滞后于架构变更。旧条目被保留成 `~~已停用~~` 形式，Agent 读到的是"存在过"这个事实。

**规则**：

- 前提条件消失的规则要**删掉**，不要留删除线版本
- `paths` 指向已删除文件，会让整条规则永不激活，且不报错
- 架构变更时，同步复审所有规则文件

## 怎么用这份案例集

**给 Agent 用**：当它违反某条规则，直接引用案例编号。例如：

> 你刚才的做法对应 CASEBOOK 案例 2。空集合不等于成功，必须显式判空。

**给自己用**：新增规则前，先问一句"这条规则对应哪次事故"。答不出来，就先别写。

**给读者用**：如果你在自己的项目里遇到相似现象，先看案例的「根因」而不是「现象」——现象会变形，根因会重复。

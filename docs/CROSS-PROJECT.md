# 跨项目共通规则

> 这份文件里的每一条规则，都在**两个以上独立项目**里出现过。
>
> 这不是巧合，是同一种失败模式在不同技术栈上的重复显形。单项目里它可能显得像个人偏好；
> 在三个项目里都撞上，说明它是**结构性问题**，不是风格问题。
>
> **这份文件的价值高于单条规则本身**：它证明这套体系不是为某一个项目定制出来的。

---

## 为什么会收敛

三个项目分别独立开发：两个 iOS（SwiftUI）、一个 HarmonyOS（ArkTS），中间还夹着一次 SDK 大版本升级。

它们由不同时间、不同代码风格、不同语言的人机协作写成，却共享同一批失败模式——这说明这些规则指向的是**语言和工具链层面的陷阱**，不是某个项目的历史包袱。

---

## 一、导航栈不可直接遍历

| 项目 | 编号 | 替代方案 |
|---|---|---|
| 项目 A（iOS 旅行类） | R001 | `Router.shared.canGoBack` / `pathCount` |
| 项目 B（iOS 日程类） | R002 | `Router.shared.currentRouteStack`（镜像栈） |
| 项目 C（HarmonyOS） | R006 | 路由统一走项目自己的封装层 |

**共通点**：框架的导航结构是私有类型或受限 API，直接遍历不可行或不稳定。两个 iOS 项目从不同角度撞上同一堵墙——一个选择「不维护平行栈」，一个选择「用镜像栈补足缺口」。

**通用表述**：导航状态只能经由**项目自己的单一封装层**读写，且该封装层必须提供**只读查询接口**（能不能回退、栈有多深），不能只提供写入。

---

## 二、错误分类与错误文案必须分离

| 项目 | 证据 |
|---|---|
| 项目 C | R016 / R017 两条正式禁止项；真实 IAP 中文返回「用户取消支付」，英文 `cancelled` 永不匹配，该分支是死代码 |
| 项目 A | ERRORS「PaywallError guard nil 反模式」——把枚举 case 当 Optional 用 |
| 项目 B | 有独立的 `AppError` 类型文件，但未成文为规则 |

**共通点**：文案是展示层的东西，会随语言变、随版本改。拿它做业务分支判断，等于把逻辑绑死在随时会变的字符串上。

**通用表述**：凡是「这件事是什么」的判断，必须用**机器可读的分类**（枚举 / 错误码），不能用「这件事怎么说」。

---

## 三、组件抽取必须全量盘点调用点

| 项目 | 证据 |
|---|---|
| 项目 B | R004；E001 invalid redeclaration——创建页迁了、编辑页没迁 |
| 项目 C | 抽 `ImagePickFlow` 之前，`EditCollectionPage` 只取了 `originalUri`、漏取 `croppedImage`，与另一处同款根因 |
| 项目 A | 结构体 init 加了 4 个时间字段放在末尾，3 个构造点只传基础字段，时间全丢 |

**共通点**：同一个根因在**三个不同项目、不同语言**里各自复发了一次。抽组件、抽 helper、改 init 签名——只要是「多处调用同一个东西」的结构变更，就必须全量盘点。

**通用表述**：任何「改一处、影响多处」的变更，改完必须列出全部调用点并逐一核对，不能只改编译器报错的那几处。

---

## 四、全局单例在测试与并发场景必须隔离

| 项目 | 证据 |
|---|---|
| 项目 A | 快照测试间歇性崩溃，根因是全局单例被并发用例改动；汇总行还显示「0 failures」 |
| 项目 C | DI 容器 `clear()` 重建单例，模块级常量与 `getInstance()` 指向两个实例 |
| 项目 B | 未记录同类案例，但存在 `Services/Mock/` + `Factories/` 同构结构 |

**共通点**：单例在运行时是优点，在测试里是**跨用例的状态泄漏源**。

**通用表述**：单例必须提供显式的重置入口；测试要么在用例间重置，要么串行执行。

---

## 五、实验分支只在本地，远端只保留主干

| 项目 | 载体完备度 |
|---|---|
| 项目 C | 最完整：R004 / R005 / R021 + 专门 `git.md` + 删分支前 `git cherry` + `git diff --name-status` 两道等价性验证 |
| 项目 B | CLAUDE.md + TRUTH 状态条目；操作前 `pwd && git rev-parse --show-toplevel` 双重确认 |
| 项目 A | CLAUDE.md 一句指针（且所引的 `rules/git.md` 实际不存在——见下方「已知缺口」） |

**共通点**：「推远端不是备份，是宣告这个分支可用」。实验分支推到远端，会成为第二份事实来源。

**通用表述**：实验分支只在本地；合并进主干后只推主干；删分支前做等价性验证，被拒时不要直接 `-D`。

## 六、编译通过不等于功能可用

| 项目 | 证据 |
|---|---|
| 项目 C | 用高版本 SDK 编译 + 低版本最低部署 → 目标设备上该能力静默不可用；切 SDK 后新冒的「API is supported since SDK version X」告警必须逐条核对，不能只看编译通过 |
| 项目 A | `@MainActor` isolation thunk 编译期完全无感，只在真机后台路径 trap |
| 项目 B | `UIRequiredDeviceCapabilities` 与二进制架构矛盾，上传被判无效二进制——签名与架构检查也不会在编译期报 |

**共通点**：三件事分别是**API 版本、运行时隔离、二进制元数据**。它们有一个共同特征：编译器和编译器都不管。

**通用表述**：版本相关能力必须按**最低部署版本**逐条核对；改动必须跑一次目标环境的真机流程。

---

## 七、用户可见的导出物同样适用文案规则

| 项目 | 证据 |
|---|---|
| 项目 C | R020：导出报告硬编码中文；且平台的格式化只做字符串替换不转义，用户数据必须先 `escapeHtml()` |
| 项目 B | `DataExportService` / `CSVExporter` 结构同构，无成文规则 |
| 项目 A | `PDFExporter` 结构同构 |

**通用表述**：凡是会离开 App 的东西——导出、分享、推送、邮件——都是用户可见文案，都要资源化；用户数据进模板前必须转义。

## 八、依赖只允许一条合法声明路径

| 项目 | 证据 |
|---|---|
| 项目 A | R003：禁 `pod install` / `xcodegen generate`；工程直接入库，无生成步骤 |
| 项目 B | 同款：无 CocoaPods / 无 XcodeGen，依赖手动在 Xcode 配 |
| 项目 C | 依赖只在 Hvigor 配置文件声明；一律优先官方 CLI，不手调底层构建脚本（手调易漏参数且**跳过签名**） |

**共通点**：不是「禁止某个工具」，是**只允许一条路径**。多一条路径就多一份状态来源。

**通用表述**：依赖声明、构建命令、签名配置各自只有一个权威位置。AI 不手改工程文件内部字段。

---

## 九、文案必须资源化，且所有语言变体同步修改

| 项目 | 证据 |
|---|---|
| 项目 C | R015 + 独立 `i18n.md`：19 条 key 误写进 AppScope → `Unknown resource name`；只改 `base/` 不改 `en_US/` 编译能过但英文环境静默回落中文 |
| 项目 A | `Localizable.xcstrings`（zh-Hans + en）+ `StringLocalizedTests` |
| 项目 B | `en.lproj` / `zh-Hans.lproj` 双份 `Localizable.strings` + 迁移完成度文档 |

**共通点**：「只改一种语言」是**静默失败**——编译过、测试过、用户切换语言才发现。

**通用表述**：文案改动必须成组提交，且有校验脚本覆盖，不靠人记得。

## 十、同一错误复发两次必须记录并升格

| 项目 | 载体 |
|---|---|
| 项目 A | 根 `ERRORS.md`（格式：时间 \| 描述 \| 根因 \| 解决） |
| 项目 B | 根 `ERRORS.md`，额外有「已升格至」列 + 状态标记（待升格 / 已升格 / 已豁免） |
| 项目 C | 端级 `ERRORS.md` + `BUGS.md`（生产 Bug 单独记） |

**共通点**：阈值完全一致——同一错误出现 **2 次以上**。

**升格路径**（项目 B 与 项目 C 都显式定义）：

```
ERRORS.md  →  rules/  →  CLAUDE.md 核心禁止表
```

一条错误只写在 `ERRORS.md` 里是浪费——它应该一路升格成一条**永久防线**。

## 十一、规则体系分层，且不允许内容重复

| 项目 | 结构 |
|---|---|
| 项目 A | `CLAUDE.md` + 4 条 rules + `TRUTH.md` + `LLM WIKI.md` |
| 项目 B | `CLAUDE.md` + 4 条 rules + `TRUTH.md` + `LLM WIKI.md` |
| 项目 C | 端级 `CLAUDE.md` + 8 条 rules + `WORKTREE.md`；跨端大文档从 `.claude/rules/` 迁到 `docs/reference/` |

**共通点与实测数据**：项目 C 项目根实测发现，跨端大文档放在 `.claude/rules/` 里（无 paths 约束 → 贪婪加载）占了启动上下文的 **80.5%（70,148 字符）**。迁出后启动上下文大幅下降。

**通用表述**：规则文件分三层——入口（常驻）/ 专项（按路径）/ 参考（按需读）。跨项目的大文档**不能**放进按路径加载的目录。

## 十二、生产代码里不留调试逻辑、假数据、占位后门

| 项目 | 证据 |
|---|---|
| 项目 A | R006 正式禁止项；历史上曾发生「启动时全局 setMock()」的假数据事故 |
| 项目 C | ERRORS：导出时下载第三方占位图并嵌入用户的 HTML 导出产物 |
| 项目 B | `Services/Mock/` + `Factories/` 结构同构，未成文 |

**通用表述**：Mock 只能经由**显式工厂**切换，Release 构建忽略一切调试覆盖。导出产物里的占位图和假数据同样是事故。

## 这些共通规则说明了什么

三条结论：

1. **规则不是个人偏好，是结构性的。** 同一个根因在三个不同语言的项目里复发，说明问题在语言和工具链，不在写代码的人。
2. **「静默失败」是最贵的失败。** 十二条里至少八条的共同点是：编译通过、测试通过、用户端才炸。这类错误值得单独的规则去拦。
3. **收敛本身就是证据。** 一套规则在一个项目里成立，是个人经验；在三个项目里都成立，就是方法论。

## 已知缺口

以下问题在分析中被发现，**尚未修复**（记录在此，避免后人重复踩）：

| 项目 | 缺口 |
|---|---|
| 项目 A | `CLAUDE.md` 引用了 `.claude/rules/git.md`，但该文件不存在——分支纪律实际无载体 |
| 项目 A | 同时存在根 `ERRORS.md` 与 `.claude/ERRORS.md` 两份；状态文件已把后者标为待删除死文件 |
| 项目 B | `CLAUDE.md` 末次更新 2026-05-25，缺 K13（写后 diff 验证） |
| 项目 B | `rules/frontend.md` 仍写「BottomButtonBar 新旧 API 并存」，而 R004 已拓宽到「所有创建页与编辑页」——rules 层未同步 R 条 |
| 项目 C | 端级 CLAUDE.md 自述 `frontend.md` 与 `arkts.md` 内容高度重复，两份都会激活 |
| 项目 C | 鸿蒙端无编号化 K 表，12 条执行规则散落复述；且 `K-2` / `K-5` 与 `K1`–`K12` 是两套编号体系，易混淆 |

**这些缺口本身就是最好的教材**：规则体系会腐化，而且腐化方式很隐蔽——引用了不存在的文件、同一规则写了两份、旧表述没跟上新规则。维护规则和写代码一样，需要定期复核。

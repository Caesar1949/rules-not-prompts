# 国际化（i18n）规则

> 适用于任何多语言项目（ArkTS / Swift / Android / Web 通用）。
> 这套规则来自一次跨端文案对齐的批量事故，见 `docs/CASEBOOK.md`。

---

## 一、文案必须资源化

**禁止硬编码用户可见文案。**

| 层级 | 放哪 |
|---|---|
| 模块资源 | `entry/src/main/resources/base/element/string.json` |
| 语言变体 | `entry/src/main/resources/en_US/element/string.json` |
| App 级（仅 app_name） | `AppScope/resources/base/element/string.json` |

代码里用 `$r('app.string.<key>')` 引用，key 统一 `snake_case`。

### `$r()` 解析的是「模块」资源，不是 AppScope

这是最容易踩的一条：

- `$r('app.string.*')` 只在**模块**的 `resources/*/element/` 下找
- 把 key 写进 `AppScope/resources/base/element/string.json` → 编译报 `Unknown resource name`
- AppScope 的 `string.json` 只保留 `app_name`，供 `AppScope/app.json5` 的 `$string:app_name` 用

**一次写错就是 19 条报错。** 改完跑一遍资源校验脚本。

### `$r()` 是编译期宏，不是运行时查找

这意味着**任何 `.ets` 层都能用**——包括 ViewModel 和 Service。

- 承载文案字段的类型要加宽为 `ResourceStr`
- 落库字段存**空串**，展示层负责回落资源默认值
- `ResourceStr` **不能取 `.length`**——它是 union 类型。用统一的 `isTextBlank()` 之类的工具函数判断

「ViewModel 拿不到 resourceManager 所以只能硬编码中文」是个伪命题。

---

## 二、所有语言变体必须同步修改

**只改 `base/` 不改 `en_US/`：编译通过，测试通过，英文环境静默回落中文。**

这是 i18n 里最贵的错误——它不会在任何环节报错，只会在用户切换系统语言时暴露。

强制措施：

- 改完跑一致性校验脚本（如 `docs/tools/i18n-parity-check.py`）
- 校验脚本应进 CI，不靠人记得

---

## 三、状态与文案分离

**不要拿文案字段的空/非空兼作「有没有错」这类状态标志。**

```
❌  errorMessage != nil  →  表示「出错了」
✅  hasError: boolean    →  表示「出错了」
```

状态用独立的布尔或枚举，文案允许为空，空时由组件内部回落资源默认。

---

## 四、文案不得参与业务分支判断

**这是最隐蔽、代价最大的一条。**

```
❌  if (errMsg.includes('cancelled')) { /* 用户取消 */ }
```

文案随语言变。真实 IAP 在中文系统返回「用户取消支付」，在英文系统返回别的说法——`includes('cancelled')` **永远匹配不上**，这个分支实际是死代码。

更糟的情况：Mock 模式下靠 `'cancelled:user_cancelled'` 这种**文案哨兵**碰巧能匹配，所以本地测不出来，一到真机就错。

**正确做法**：错误**分类**（机器可读）与错误**文案**（展示）分离。

```
enum PurchaseErrorKind { userCancelled, networkFailed, unknown }
```

页面只看分类码，文案只管显示。

**判断依据**：这段逻辑依赖的是「这件事是什么」，不是「这件事怎么说」。凡是后者，一律不能用来分支。

---

## 五、占位符按平台语法

| 平台 | 语法 |
|---|---|
| ArkTS | `%d` / `%s` / `%f` |
| Swift | `%@` / `%lld` |
| Android | `%1$d` / `%s` |

跨端同一文案要各写各的占位符。

---

## 六、不要拿中文当 key

key 用 `snake_case` 的语义名（如 `error_network_timeout`），不要用中文原文。中文会改，key 改了就是一次静默的文案丢失。

跨端项目的 key 建议维护一张**基准表**，各端对齐同一套命名。

---

## 七、导出物里的文案同样适用

生成给用户的外部文档（HTML / PDF / CSV）不读 `resourceManager`，但它**同样是用户可见文案**。

- 文案走对应资源，用项目统一的 `getStringSync` 之类的方式解析后注入
- ⚠️ **平台的格式化函数只做字符串替换、不做转义**——用户数据（标题、品牌名、日期）必须**先 HTML 转义**，再作为占位符参数传入

不做这一步：英文系统导出的报告满屏中文，且用户输入的 `<` `&` 会破坏文档结构，甚至造成注入。
